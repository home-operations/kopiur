By default, Kopiur runs each mover Job in the namespace of the `Snapshot` or the
`Restore`, beside the PVC. **Central execution** moves the Job to the operator
namespace. You turn it on with one field on a `ClusterRepository`.

:::caution[Experimental: central backups depend on an alpha Kubernetes feature]

A central backup uses the `CrossNamespaceVolumeDataSource` feature. That feature
is alpha in Kubernetes and off by default. A cluster administrator must turn it
on in three places. Kubernetes can change or remove an alpha feature, so do not
make this your only backup path.

A central restore, a verification, a pin, and a browse session do not use that
feature. They need no feature gate.

:::

## When you want this

A mover in the workload namespace has two costs:

- The repository credentials must be readable in that namespace, because a pod
  can only load a Secret from its own namespace.
- A pod that holds those credentials runs beside tenant workloads.

With central execution, the workload namespace holds no repository credentials
and runs no mover pod. Tenants do not change their `SnapshotPolicy`.

Do not use it for PVC backups when your storage has no CSI snapshot or clone
support, or when you cannot change the feature gates of the cluster. The default
placement works on any storage.

## What runs where

| Work                                                               | Under `execution.mode: Central`                                           |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Backup of a PVC, `copyMethod: Snapshot` or `Clone`                 | Operator namespace                                                        |
| Backup of a `groupBy: VolumeGroupSnapshot` group                   | Operator namespace, one mover for each member                             |
| Backup of an NFS source                                            | Refused. See [Limits](#limits).                                           |
| Backup of a PVC, `copyMethod: Direct`                              | Refused. A pod can only mount a PVC from its own namespace.               |
| Backup of a `stream` source                                        | Refused. The mover must run a command in a pod of the workload namespace. |
| Restore, `target.populator`                                        | Operator namespace                                                        |
| Restore, `target.pvc`, when the PVC does not exist yet             | Operator namespace                                                        |
| Restore into an existing PVC (`target.pvcRef`, or an existing PVC) | Workload namespace. The mover must mount that PVC.                        |
| Restore, `target.streamExec`                                       | Workload namespace. The mover must run a command in a pod there.          |
| Verification (`spec.verification`)                                 | Operator namespace                                                        |
| Snapshot pin (`spec.pin`)                                          | Operator namespace                                                        |
| Browse session (`kubectl kopiur browse`, the web console)          | Operator namespace. You need your own access to that namespace.           |
| Maintenance, snapshot deletion                                     | Operator namespace, as for every `ClusterRepository`                      |
| Hooks                                                              | Workload namespace. See [Limits](#limits).                                |

"Refused" means that the `Snapshot` fails with the reason
`CentralExecutionUnsupported`. Kopiur never falls back to a mover in the
workload namespace for a backup.

The two restores that stay in the workload namespace need the repository
credentials there, by a Secret that you create or by
[credential projection](/restores/#credentials-in-a-fresh-namespace--credentialprojection).

## How it works

A pod can only mount a PVC from its own namespace. The data therefore crosses
namespaces as a CSI snapshot.

```text
workload namespace (billing)             operator namespace (kopiur-system)

  PVC postgres-data
        |
        v  1. snapshot
  VolumeSnapshot  <---- 3. dataSourceRef ----  staged PVC
  ReferenceGrant  (2. permits step 3)              |
                                                   v  4. mount
                                               mover Job  ---->  repository
```

1. Kopiur creates a `VolumeSnapshot` of the source PVC in the workload namespace.
   This is the same step as [`copyMethod: Snapshot`](/copy-methods/).
2. Kopiur creates a `ReferenceGrant` beside the `VolumeSnapshot`. The grant names
   that one `VolumeSnapshot` and the operator namespace.
3. Kopiur creates the staged PVC in the operator namespace. Its
   `spec.dataSourceRef` points at the `VolumeSnapshot` in the workload namespace.
4. The mover Job runs in the operator namespace, reads the staged PVC, and
   writes to the repository.
5. Kopiur deletes the staged PVC, the `VolumeSnapshot`, and the `ReferenceGrant`.

The `Snapshot` object stays in the workload namespace. Its status, events, and
retention work as before.

The other sources cross in a similar way:

- **`copyMethod: Clone`.** There is no `VolumeSnapshot`. The `dataSourceRef` of
  the staged PVC points at the source PVC, and the `ReferenceGrant` names that
  one PVC. The CSI driver clones the volume into the operator namespace.
- **`groupBy: VolumeGroupSnapshot`.** One `VolumeGroupSnapshot` captures all
  the PVCs in the workload namespace. Each member then gets its own staged PVC
  and its own mover in the operator namespace, with a `ReferenceGrant` for its
  own member snapshot.

### Where the source is mounted

A central mover pod mounts every source at the fixed path `/source`. The pod
holds the repository credentials, so a tenant must not choose a path in it. A
volume mounted over the mover binaries would run tenant code with those
credentials.

The path that kopia **records** does not change. It is `/pvc/<name>` by default,
or the `sourcePathOverride`. A central backup and a backup in the workload
namespace record the same path, so both belong to the same snapshot history.

A filesystem repository must not keep its files at `/source`, or at a path
inside or above it. The mover pod mounts the repository volume at the path of
the repository, and two mounts cannot overlap. Kopiur refuses such a backup
with the reason `CentralExecutionUnsupported`.

### Where a persistent cache lives

A `mover.cache` with `mode: Persistent` keeps the kopia cache of a mover between
runs. See [Sizing the kopia cache](/backups/#sizing-the-kopia-cache). Under
central execution, Kopiur creates the cache PVC in the operator namespace,
because the mover pod can only mount a PVC from its own namespace. You change
nothing in the `SnapshotPolicy` or the `Restore`.

For a backup, the cache belongs to the `SnapshotPolicy`:

- The first run of a policy creates the PVC. Each later run mounts the same
  PVC, so it starts with the cache of the run before.
- The PVC is named `kopiur-cache-<policy>-<hash>`. The hash is made from the UID
  of the policy and the repository, because policies from many namespaces share
  the operator namespace. A policy with more than one repository gets one PVC
  for each repository.
- A policy with a `pvcSelector` source gets one PVC for each source PVC, also
  under `groupBy: VolumeGroupSnapshot`. Such a policy runs one mover for each
  source at the same time, and those movers cannot share a `ReadWriteOnce`
  volume. Each of these PVCs has the full `capacity`.
- A higher `capacity` grows the PVC on the next run, as it does in the workload
  namespace. The Events about the PVC appear on the `SnapshotPolicy`. They name
  the PVC with its namespace, for example `kopiur-system/kopiur-cache-…`.
- The PVC is `ReadWriteOnce`, so the runs of one policy for one source must not
  overlap. This is the same rule as in the workload namespace.

For a central restore, the cache belongs to the `Restore`:

- Each mover Job of the restore gets its own PVC, named
  `kopiur-cache-<restore>-<hash>`. A restore has one mover Job for each PVC
  that claims it.
- The PVC stays until you delete the `Restore`. A new attempt of the same mover
  Job mounts it again.

In both cases the workload namespace holds no cache PVC.

#### Find the cache PVC

A tenant has no access to the operator namespace, so Kopiur reports the PVC on
objects the tenant can read:

- Each `Snapshot` records the PVC that its mover mounted.
- A `CachePvcCreated` Event on the `SnapshotPolicy` or the `Restore` names the
  PVC when Kopiur creates it.

```console
$ kubectl get snapshot -n billing postgres-data-20260706 -o jsonpath='{.status.resolved.cache.claim}'
{"name":"kopiur-cache-postgres-data-94c57734fbfe76da","namespace":"kopiur-system"}
```

An administrator can list the cache PVCs in the operator namespace. On the PVC
of a central backup or restore, an annotation names the owner as
`<namespace>/<name>`: `kopiur.home-operations.com/policy` for a
`SnapshotPolicy`, and `kopiur.home-operations.com/restore` for a `Restore`.

```console
$ kubectl get pvc -n kopiur-system -l kopiur.home-operations.com/component=mover-cache
```

#### Reset the cache

A tenant cannot delete a PVC in the operator namespace. To delete the cache
PVCs of a policy, set the annotation
`kopiur.home-operations.com/cache-reset-requested-at` on the `SnapshotPolicy`
to a new value. See [Reset a persistent cache](/backups/#reset-a-persistent-cache).
Do this to apply a smaller `capacity` or a different `storageClassName`.

#### What a tenant controls

A tenant sets the `capacity` and the `storageClassName` of this PVC. The volume
is in the operator namespace, so a `ResourceQuota` of the workload namespace
does not count it. To limit it, set a quota on the operator namespace.

The PVC holds the kopia cache and nothing else. The repository credentials are
not on it. See
[What a cache volume holds](/backups/#what-a-cache-volume-holds).

If a PVC of that name exists and does not belong to the policy or the restore,
Kopiur does not mount it. The run gets a new volume of the same capacity
instead, and a `CachePvcNameConflict` Warning Event on the `SnapshotPolicy` or
the `Restore` names the PVC.

### How a restore works

A central restore hands a finished volume to a PVC in the workload namespace.
That PVC claims the `Restore` through its `spec.dataSourceRef`. There are two
ways to get such a PVC:

- **`target.populator`.** You write the PVC, with a `dataSourceRef` to the
  `Restore`.
- **`target.pvc`.** Kopiur creates the PVC for you, with that `dataSourceRef`.
  This applies when no PVC of that name exists and there is a snapshot to
  restore. If a PVC of that name exists, the restore writes into it in place,
  from a mover in the workload namespace. If there is no snapshot and
  `onMissingSnapshot` is `Continue`, Kopiur creates an ordinary empty PVC, and
  no mover runs anywhere.

1. Kopiur creates a temporary **prime PVC** in the operator namespace. It copies
   the size, the StorageClass, and the access modes of the claiming PVC. If the
   StorageClass uses `WaitForFirstConsumer`, a `target.populator` restore first
   waits until a pod that uses the claiming PVC is scheduled, as for every
   populator restore. A `target.pvc` restore does not wait: the mover pod is the
   first consumer, and the volume is created on the node where the mover runs.
2. The mover Job runs in the operator namespace and restores the snapshot into
   the prime PVC.
3. Kopiur hands the volume to the claiming PVC. A `PersistentVolume` is not
   bound to a namespace, so Kopiur points the volume at the claiming PVC and
   deletes the prime PVC.
4. The claiming PVC binds to the volume, and the workload can mount it.

This uses only stable Kubernetes APIs. The `Restore` object stays in the
workload namespace.

## What the cluster needs

A cluster administrator must provide all of these. Kopiur cannot set them up.
Only a central backup of a PVC needs the first five rows. Everything else needs
only the last two.

| Requirement                                                                         | Where                                                                  |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Feature gate `CrossNamespaceVolumeDataSource=true`                                  | kube-apiserver and kube-controller-manager                             |
| Flag `--feature-gates=CrossNamespaceVolumeDataSource=true`                          | the `csi-provisioner` (external-provisioner) sidecar of the CSI driver |
| `get`, `list`, `watch` on `referencegrants.gateway.networking.k8s.io`               | the ServiceAccount of that `csi-provisioner`                           |
| The `ReferenceGrant` CRD (`gateway.networking.k8s.io/v1beta1`)                      | the cluster (it ships with the Gateway API CRDs)                       |
| The CSI snapshot stack and a `VolumeSnapshotClass` for the driver of the source PVC | the cluster (see [Copy methods](/copy-methods/))                       |
| A cluster-scoped Kopiur install (`installScope: cluster`)                           | the Helm release                                                       |
| The repository credential Secret, and the PVC of a filesystem backend               | the operator namespace                                                 |

:::danger[Set the provisioner flag and its RBAC together]

When the feature gate is on, the `csi-provisioner` reads `ReferenceGrant` objects
at startup. If the CRD or the RBAC rule is missing, the provisioner does not
become ready, and the driver provisions no volumes at all. Install the CRD and
the RBAC rule first, then set the flag.

:::

### What happens when the API server gate is off

With the gate off, kube-apiserver removes the `dataSourceRef` from the staged PVC
and stores a claim for an **empty** volume. A backup of that volume would succeed
and contain nothing.

Kopiur reads the stored claim back before it starts the mover. If the reference
is gone, Kopiur deletes the claim and fails the `Snapshot` with the reason
`CrossNamespaceDataSourceDisabled`. No backup is taken.

## See where a backup ran

The `Snapshot` records the mover Job in its status:

```console
$ kubectl get snapshot -n billing postgres-data-20260706 -o jsonpath='{.status.job}'
{"name":"postgres-data-20260706-1f0c7a55d2e9b6a4","namespace":"kopiur-system"}
```

`status.job.namespace` is present only for a central backup. The Job name is the
`Snapshot` name plus a hash of its namespace and name, because Jobs from many
namespaces share the operator namespace.

A central `Restore` records the namespace in `status.execution.namespace`:

```console
$ kubectl get restore -n billing postgres-data-restore -o jsonpath='{.status.execution}'
{"namespace":"kopiur-system"}
```

Read the mover log with `kubectl kopiur logs snapshot <name> -n billing` or
`kubectl kopiur logs restore <name> -n billing`. The command follows the status
to the operator namespace, so you need read access to Jobs and pods there.
Without that access, read the recorded log tail: `status.logTail` on a
`Snapshot`, and `status.claims.<pvc>.logTail` on a populator `Restore`.

## Limits

- **A restore into an existing PVC runs in the workload namespace.** This is
  `target.pvcRef`, and `target.pvc` when a PVC of that name exists. The mover
  must mount that PVC, and a pod can only mount a PVC from its own namespace. A
  `target.streamExec` restore also runs there, because the mover runs a command
  in a pod of that namespace. See [What runs where](#what-runs-where).
- **`copyMethod: Direct` and `stream` sources are refused**, for the same two
  reasons. The `Snapshot` fails with `CentralExecutionUnsupported`.
- **Do not delete the source PVC during a `copyMethod: Clone` backup.** The
  CSI provisioner protects a PVC from deletion while a clone of it is in
  progress. That protection only sees clones in the namespace of the source. A
  central clone is in the operator namespace, so the provisioner lets the
  deletion go ahead, and the backup then fails. `copyMethod: Snapshot` has no
  such limit.
- **NFS sources are refused.** The mover pod itself mounts an NFS export. A
  namespace can forbid `nfs` volumes for its pods (the `restricted` Pod Security
  level does). A mover pod in the operator namespace does not obey that rule of
  the workload namespace. A tenant could then make it mount any export that the
  nodes can reach. Back up an NFS source with a repository that does not set
  `execution.mode: Central`.
- **Browsing needs access to the operator namespace.** You create the session
  Job and exec into its pod as yourself. A user with no rights in the operator
  namespace cannot browse a snapshot of a central repository. Such a user can
  still restore it.
- **A restore does not change site in the middle of its work.** A central
  `Restore` stays central if you remove the field. A `Restore` that has claims
  in progress or finished in its own namespace stays there if you set
  `execution.mode: Central` later. It moves to central execution only when none
  of its claims is in progress or finished, for example after you re-create its
  claiming PVC.
- **Hooks still act in the workload namespace.** The controller runs
  `workloadExec` hooks through the API server. A `runJob` hook creates its Job
  in the workload namespace. Neither one uses the repository credentials.
- **A privileged mover needs the opt-in on both namespaces.** A mover that
  needs root requires the `kopiur.home-operations.com/privileged-movers`
  annotation on the workload namespace, as always. The pod runs in the operator
  namespace, so that namespace needs the annotation too. The pod must also pass
  the Pod Security level of the operator namespace. This applies to backups,
  restores, and verification.
- **A `ClusterRepository` only.** A central mover takes the credential Secrets,
  and the PVC of a filesystem backend, from the operator namespace by name. Only
  a `ClusterRepository` can name them. If you point a central backup or restore
  at a namespaced `Repository` after it started, Kopiur refuses to launch it.
- **Zonal volumes.** The staged PVC and the mover pod must land in the zone of
  the snapshot. Kopiur adds no placement rule for this. A persistent cache PVC
  stays in the zone, or on the node, where its first run put it. The later
  movers of that policy can only run there.
- **The operator keeps its cluster-wide RBAC.** Central execution keeps movers
  and credentials out of tenant namespaces. It does not yet reduce the
  permissions of the controller.

## When a backup fails

Each of these appears as the reason of the `SourceStaged` condition on the
`Snapshot`, with a message that states the fix. The `Snapshot` is `Failed`. The
next scheduled run, or a new `Snapshot`, tries again.

| Reason                             | Meaning                                                                                                                                                                            |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CentralExecutionUnsupported`      | The policy uses `copyMethod: Direct` on a PVC, a `stream` source, or an NFS source.                                                                                                |
| `CentralExecutionUnavailable`      | The install is namespace-scoped, or the controller has no `KOPIUR_NAMESPACE`.                                                                                                      |
| `ReferenceGrantCRDMissing`         | The `ReferenceGrant` CRD is not installed.                                                                                                                                         |
| `CrossNamespaceDataSourceDisabled` | The feature gate is off on kube-apiserver. Kopiur deleted the empty claim.                                                                                                         |
| `StagedPvcBindTimeout`             | The staged PVC did not bind. The usual cause is the provisioner flag or its `referencegrants` RBAC rule. For `copyMethod: Clone`, the CSI driver must also support volume cloning. |
| `CentralObjectNameConflict`        | A PVC with the derived name belongs to another `Snapshot`. Kopiur does not use or delete it.                                                                                       |

A missing credential Secret in the operator namespace appears as
`CredentialsAvailable=False`, as it does for any mover.

## Cleanup

### After a backup

The Job and the staged PVC cannot carry an owner reference to the `Snapshot`,
because an owner must live in the same namespace. Kopiur labels them with the
UID of the `Snapshot` (`kopiur.home-operations.com/snapshot-uid`) and records
their location in `status.job`.

- The staged PVC, the `VolumeSnapshot`, and the `ReferenceGrant` go when the
  backup finishes or fails.
- The Job goes when you delete the `Snapshot`, or earlier by
  `ttlSecondsAfterFinished`.

Deleting a `Snapshot` at any point, also while its stage is still being
prepared, removes all of these objects.

The CSI external-provisioner (v6.3 and later) does not remove its protection
finalizer from the `VolumeSnapshot` after a cross-namespace restore. See
[external-provisioner issue 1613](https://github.com/kubernetes-csi/external-provisioner/issues/1613).
Without help, the deleted `VolumeSnapshot` stays `Terminating` until the
periodic sweep of the provisioner runs (5 minutes by default), or for good where
that sweep is off.

Kopiur therefore tries to remove that finalizer itself, when all of these are
true:

- Kopiur already deleted the `VolumeSnapshot`.
- Kopiur saw the staged PVC of the backup bound. That proves the restore from
  the `VolumeSnapshot` finished.
- No unbound PVC in the cluster restores from the `VolumeSnapshot`. The sweep
  of the provisioner uses the same test.

This step is best effort. If a backup stops while its staged PVC is still being
provisioned, Kopiur cannot prove that the restore finished. If an API call for
this step fails, Kopiur does not retry it for long. In both cases Kopiur leaves
the finalizer to the provisioner.

If you remove the finalizer of a `Snapshot` by hand, Kopiur does not run this
cleanup. Find leftovers with:

```console
$ kubectl get jobs,pvc -n kopiur-system -l kopiur.home-operations.com/snapshot-uid
```

After a `copyMethod: Clone` backup, the CSI external-provisioner leaves its
`provisioner.storage.kubernetes.io/cloning-protection` finalizer on the source
PVC. This is how the provisioner works for every clone, also in the workload
namespace. The provisioner removes the finalizer when you delete the PVC.

### After a group backup

Kopiur deletes the shared `VolumeGroupSnapshot` when every member of the group
finished and released its staged PVC. It then deletes the member
`VolumeSnapshot` objects and removes the provisioner finalizer from each one, by
the rule above.

### After a verification or a pin

A central verification Job is labelled with the UID of the `SnapshotPolicy`
(`kopiur.home-operations.com/policy-uid`). It expires by its
`ttlSecondsAfterFinished`. Kopiur deletes the Jobs that remain when you delete
the policy.

A central pin Job is labelled with the UID of the `Snapshot`. Kopiur deletes it
when it has recorded the result, or when you delete the `Snapshot`.

### A persistent cache

A central cache PVC is labelled with the UID of its owner:
`kopiur.home-operations.com/policy-uid` for a `SnapshotPolicy`, and
`kopiur.home-operations.com/restore-uid` for a `Restore`. Kopiur deletes the
PVC when you delete that policy or that restore.

Kopiur also deletes a cache PVC that nothing uses any more. A periodic cleanup
does this, every 6 hours by default. It only deletes a PVC that is at least
1 hour old. See [The object sweep](/movers/#the-object-sweep) for the two
settings. The cleanup deletes a central cache PVC in these cases:

- Its `SnapshotPolicy` or `Restore` no longer exists.
- Its policy no longer backs up to the repository of the PVC.
- The repository no longer sets `execution.mode: Central`.
- The policy no longer has a `mode: Persistent` cache with a `capacity`.
- The source PVC that it serves no longer exists, or the `pvcSelector` of the
  policy no longer matches it.

A policy that now keeps its cache in the operator namespace can have an older
cache PVC in its workload namespace (`kopiur-cache-<policy>`). The cleanup
deletes that PVC too.

The cleanup deletes nothing of a policy while one of its `Snapshot` objects is
`Pending` or `Running`. If a mover pod still mounts a PVC, the PVC goes after
that pod ends. To delete the cache PVCs of a policy without the wait for the
cleanup, [reset the cache](#reset-the-cache).

:::note[After a downgrade]

Kopiur 0.11.1 and earlier do not know these PVCs. If you downgrade, delete the
central cache PVCs by hand. Find them with the `kubectl get pvc` command in
[Find the cache PVC](#find-the-cache-pvc).

:::

### After a restore

The prime PVC and the mover Job also cannot carry an owner reference to the
`Restore`. Kopiur labels them with the UID of the `Restore`
(`kopiur.home-operations.com/restore-uid`).

- Kopiur deletes the prime PVC and the Job when it hands the volume over.
- A central `Restore` carries the finalizer
  `kopiur.home-operations.com/central-restore-cleanup`. When you delete the
  `Restore`, Kopiur deletes any prime PVC and Job that remain, and its
  persistent cache PVCs, and then removes the finalizer.

## RBAC

Central execution adds one mover identity and one controller rule. See
[RBAC reference](/rbac/#the-central-mover-kopiur-central-mover).

To browse a snapshot of a central repository, a user needs the browse
permissions in the operator namespace. See
[RBAC reference](/rbac/#browsing-snapshots-rbacbrowserole).
